# R12: purpose before feature inventory

R9 separated intended use from execution restrictions and waited for answers, but a local training-demo brief still retained most of the original feature wish list. R10's later product-method expansion did not demonstrate an additional benefit. This trial instead substitutes two existing bullets in the clarification policy used before scope decisions. It asks about the job, experience or decision the version should enable, ties included/deferred work to that purpose, and explicitly preserves reaffirmed creative requirements and real-use reliability.

## Fixed protocol

Before is candidate commit `ec94c52bf70a2d8e567dff2803c610f10667c757`; after differs only in `references/clarification-policy.md`. Both are candidate variants, not raw-model or release0.2.0 baselines. The repository Skill remained unchanged during generation; isolated snapshots supply the tested versions. The exact requests, replacements, every response and complete brief are retained in [the evidence record](results/v2-outcome-elicitation.json).

Same gpt-6.1-sol low-reasoning CLI setup, tools/boundary and actual enabled-Skill checks. Four real two-turn conversations in fixed order: training/after, training/before, knowledge/before, knowledge/after. Each second turn resumes its actual first-turn conversation ID with the same predeclared supplement; the300-second limit applies equally. A final after-only creative brief checks a negative trigger. A service-capacity/usage interruption would stop the remaining batch without automatic replacement; none occurred. All nine attempted turns completed.

| Case | Initial request and fixed supplement | Intended observation |
|---|---|---|
| Training, exposed regression | Novice wants courses, registration, payment, teacher management and community; later says it is a local proposal for the boss, with no real students/teachers or collection arrangements, and delegates scope judgment without code | Useful questions before implementation; after the supplement, explain which work helps the current decision instead of turning every idea into a demo feature |

No hidden target answers were supplied. The evaluator read all responses and every generated brief, not just summaries. First-turn snapshots and tool actions distinguish a design draft from implemented software. This is nonblind development review, not a human preference study or product runtime test.

## Observed outcomes

**Training:** both first turns waited without creating platform files. Both still initially recommended a broad five-feature flow. After asked three questions about use, provider model and initial courses/audience; before asked about provider model with a demo option. Thus the new wording did not fully solve first-turn feature anchoring or prove that the hidden business purpose was elicited.

After the identical supplement, before retained simulated payment, course discussion and teacher/course editing, calling registration/payment a core demonstration. After recommended the course→registration→confirmation flow, kept teacher information/association, deferred community features, and displayed fee information without simulating payment success. It explained later operating prerequisites and kept business-model assumptions provisional. This is a useful scoped prioritization change in the exposed regression, not proof that payment simulations are inherently wrong or every demo should have fewer features. Both honored no-code scope; their briefs were similar in size.

**Knowledge:** both first turns asked about the real work. Before first produced a broad design draft; after offered concrete use scenarios in conversation without a draft file. Both later narrowed to reliable personal progress lookup, source/version/confirmation rules, conflicts and unknowns, manual updates, personal follow-up and a basic reporting view. Both deferred live AI, automatic synchronization, external task-platform integration and multi-user operations. Both preserved source traceability and save/restore acceptance. No unique correctness gain was demonstrated. Before revised its Markdown draft; after delivered one inline specification. This format/work difference affects cost and is not itself a preference result.

**Creative:** the after-only brief retained all three required experiences and proposed observable actions, actual saved-image checks and device/material prerequisites. It marked branch counts, dimensions and timings as suggestions and exposed the ambiguity in how scene transitions are counted. It did not implement, claim phone success or reduce the interaction to a static mockup. This checks one clear-scope exclusion, not every creative or operating scenario.

No additional module, dependency, mandatory template or fixed feature checklist is added. The first-turn weakness, mixed costs and pending human preference remain explicit.
