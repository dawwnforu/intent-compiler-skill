## 首次观察：从领取到实际采用

开始前问：“你愿意让我在本地记录操作步骤、耗时、卡点和你主动给出的反馈吗？可以不用真名、不分享完整对话，随时退出。查看脱敏需求或产物另问，不默认同意。”不同意则不记录其操作；撤回后按事先约定处理可识别记录。

按实际过程记录：收到包→按一页说明安装→确认实际选用项目候选→合成练习→本人真实待办→查看文件→提出修改→采用/待修改/放弃。先让对方说明目的和原来怎么做，不预先代写“完美提示词”。卡住就正常帮助并记录，不为独立完成率拒绝帮助。合成练习、真实任务及作者内部自测分别记；空表不是反馈。

`task_purpose` 开头标“合成上手／本人真实任务／作者自用”再写具体用途。统计人数按匿名代号去重，不按事件行数；真实业务完成和采用不计合成练习或作者自用。

原始表述记在 `interview_answer` 或另行同意的 `original_request_local_ref`；实际行为记在 `observed_actions`；开发者解释单独记 `developer_interpretation`。本人说“感觉不错”不等于采用；`adoption_status` 写 `adopted / needs_revision / not_adopted / unknown`，保留实际使用依据或未采用原因。原有做法优先用已有工作记录或相近任务；差异和先后学习影响写进观察，不强迫同一任务重复三遍。

## 专业任务：按成果与干预记录，不给模型理解力打印象分

在生成前，用现有合同、接收方规范或实际用途确定少量可判断的验收项，记录来源、适用范围、检查方法及不能牺牲的业务功能。不能把专家清单偷偷写进某一组的用户请求。没有明确标准时先保留待定，不用开发者偏好替代。用户仍用自己的话提需求，不必先学术语。

界面任务还要保留已认可的配色、字体、布局和导航位置，找回“这个颜色／这里”所指的截图或区域；缺失的指代不能当成已知风格。功能结果、实际视觉检查和用户偏好分别记录，不能用逻辑通过证明美观或理解到位。对照应使用相同的目标尺寸和可用参考；压缩对话、遗漏图片、改变技术环境等会影响比较，须明确记录。沿用现有访谈和验收记录，不新增主观理解力评分表。

沿用当前记录表，新增字段的含义如下；主持人记录，参与者无需填表：

| 字段 | 记录方法 |
| --- | --- |
| `delivery_criteria_local_ref` | 本地验收记录的位置，包含预先确定的标准、逐项结果、产物版本及检查者身份。开发者检查、作者自用和外部使用者验收分别注明。 |
| `delivery_acceptance` | `pass / partial / fail / unverified`。需要的文件和实际操作通过才记 pass；只写完成汇报、只列检查项或全部拒绝都不算合格。采用与验收分开。 |
| `professional_prompt_count` | 实际补充专业方法或修正专业错误的用户消息次数；同条消息含多项算一次。记录实际发生次数，未观察留空。 |
| `professional_prompt_local_ref` | 经同意保留的提示原话或脱敏摘要，逐条标时间及原因。不能为了凑低次数拒绝帮助。 |
| `clarification_count` | 正常补充业务事实、用途、偏好或授权的消息次数；这些不算专业救场。混合消息在摘要中注明两类，分别计数，不能把两列相加称总消息数。 |

现有 `rework_count` 计交付给检查者后，因未满足已确认标准而要求修改并再次交付的轮数。新需求或偏好变化不算质量返工，记在 `observed_actions`；模型在第一次交付前自行修命令、修代码属于内部修复，也不算用户返工。缺失或未观察的次数留空；“未给予专业提示”不等于“不需要专业提示”，未修复失败仍保留 fail/partial。

同模型对照还需固定模型与版本、输入材料、工具权限、调用预算和各组收到的用户补充，并保留每次产物。历史实物参照若缺原模型/Skill快照，单独描述，不能与新重放合成因果提升。优先记录合格性、专业干预、返工与实际人工时间，不把成熟模型通常已能理解用途的能力包装为 Skill 独有收益。不以降低模型能力、总对话轮数或更短输出制造优势。

例如用户说“客户只能看到自己的记录”是在说明业务约束；专家后补“仅隐藏按钮不够，还要验证接口和导出内容”才属于专业干预。用户接受某种恢复方式是决策，不能算自己教会了模型加密方法。内部固定补充与真实用户帮助分别标注，不能用模型扮演的用户填真实反馈。

每个实际观察事件一行，以 `session_id` 区分事件、`participant_alias` 关联同一人；`observed_at` 写真实带时区时间，`followup_stage` 用 `first / day1 / day7 / later`。`candidate_package_commit` 记录实际领取包的承载提交：当前af3d2c8包记 `d4648d8375456fe7a11c29d9f498a98573c03040`，其包内sourceCommit为 `af3d2c80e37e77b03d661fd803422f949d04ee89`，二者不要混用。已有239553d记录或其他实际版本如实保留，不批量改成最新候选。未发生不建行，失联/暂停只在真的发生后记原因。未知留空，不填0或预设日期。

人工时间分开记分钟：`installation_help_minutes`、`business_explanation_minutes`、`result_revision_minutes`。`human_help_minutes` 只作这三项合计，汇总时不能把总计与分项再相加；同一分钟只归一类。模型等待写 `model_wait_minutes`，研究访谈写 `research_interview_minutes`，不把它们当常规每单人工支持。整体经过时间仍可包含等待，不能与这些分项重复相加。现金工具支出仅填实际账单或明确分摊依据；未知留空，token不是现金账单。

## 复用：等真实时间和任务发生

首次结束后，按对方同意的联系范围安排次日、第7天简短询问；不创建自动跟踪，不预填7天成功。先问这段时间是否出现相关任务，再问有没有使用以及谁先提出：

- `relevant_task_available`：`yes / no / unknown`；没有任务与有任务但不想用分别保留。
- `reuse_trigger`：`spontaneous / reminded / not_used / unknown`；提醒后复用不能写主动复用。
- 在 `observed_actions` 标清是亲眼观察，还是本人回忆报告；采访回答与观察不要混算。
- `reuse_within_7_days` 只记已有事实；未到时间/未得到答复留空，不把未回复当已使用。退出、未完成和失联保留。

## 结束沿用六个短问题

1. 按开始时确定的用途和标准，哪些交付已合格，哪些没过？哪一步省事或更麻烦？
2. 若不用它，你通常怎么做？本次实际少了或多了什么？
3. 结果是否实际采用？补过几次专业方法、返工几轮，谁帮了你？普通业务补充另记。
4. 后续是否遇到新任务、是否真的复用，为什么使用或放弃？
5. 拿到交付价值后，分别问：场景材料、维护更新、人工上手服务，哪项值得付费、哪项不值得，具体为什么？金额假设另问，不把三种产品混成一个19美元问题。
6. 是否愿意另行允许查看本次脱敏产物？不提供不影响试用。

原话记在现有访谈字段，不另建问卷。口头愿意、试用申请、实际订单、退款分别统计；未收费时订单和退款为0，意愿不算订单。未查询到账保持未知，不能把模型应计收入写成到账。

## 下一轮决定

先看专业交付是否合格并被采用、需要多少专业提示与返工、实际人工时间和自然复用。基础模型本来已能理解用途不算 Skill 独有收益；专业提示少也必须保留必要功能与完成度。重复出现的安装卡点先修安装；交付反复人工重做先定位具体缺口；有任务却不用则问原因并调整场景；没有任务不直接判产品失败。任何客户包泄露先停止发送并修复回归。初步以至少2人完成合法交付、且有人在7天内实际复用作为考虑扩大下一批的观察依据，不给总体转化或付费背书。实际收费、联系平台或真实数据分享仍需对应授权。
